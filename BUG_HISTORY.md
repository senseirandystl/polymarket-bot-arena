# Bug History (avoid re-introducing)

Historical bugs and their fixes. Read before touching the resolver, discovery,
learning, or P&L code so you don't re-introduce a class of bug that's already
been fixed once.

1. **Circular learning (v3 bug, CRITICAL):** `resolve_trades()` used `market.get("current_price")` at resolution time. Resolved markets have price ~1.0 or ~0.0, so learning was: "high price = YES wins" (tautology). **Fix:** Store features at trade time in `trade_features` column.

2. **P&L always $0 (v3 bug):** Old `resolve_trades()` SELECT didn't include `shares_bought`, so the try/except defaulted to shares=0, making pnl=0 for all trades. **Fix:** Include shares_bought in SELECT, formula: `pnl = (shares - amount) if won else -amount`.

3. **P&L formula wrong (v3 bug):** Used `pnl = amount` for wins instead of `shares_bought - amount`. In prediction markets, profit = shares * $1 - cost, not 2x the bet.

4. **Stale trades clogging queue:** 5-min market trades that fell off Simmer's resolved API (limit=200) stayed pending forever (425 trades). **Fix:** Auto-expire trades pending >1h.

5. **Duplicate trades on restart:** In-memory `traded` set reset every restart. **Fix:** Load recent (bot, market) pairs from DB on startup.

6. **sqlite3.Row has no .get():** Use `try: val = row["col"] except: val = default` instead of `row.get("col", default)`.

7. **Paper P&L always $0 — resolver scanned a list that excludes fast-5m markets (CRITICAL):** `TradeResolver._resolve_pending()` fetched `/api/sdk/markets?status=resolved&limit=200` and matched pending trades against that list. BTC 5-min markets are tagged `fast-5m` and are **absent from the general market list** (the same reason `discovery.py` must pass `tags=fast-5m`), so the list never contained our markets → `resolved_map` was always empty → every trade sat pending until the 1h stale-sweep expired it at `pnl=0`. The resolver logged only `Expired N`, never `Resolved N`. **Fix:** resolve each distinct pending `market_id` by direct lookup `GET /api/sdk/markets/{id}` (`arena/resolver.py::_fetch_market_outcome`). Note: Simmer leaves `resolved_at` **null even after resolution** on these markets, so the authoritative signal is `status == "resolved"` **and** a non-null boolean `outcome` (JSON `true`/`false` = Up/Down) — do *not* rely on `resolved_at != null` here despite what the Simmer docs suggest.

8. **Paper P&L always $0 — wrong share-count field from Simmer trade response:** `_execute_paper()` logged `shares_bought=result.get("shares_bought")`, but Simmer's `/api/sdk/trade` response reports the fill under `shares` / `shares_filled` (+ `fill_price`/`cost`), *not* `shares_bought`. Missing/zero shares means `pnl = shares - amount` can only ever be $0 (same class as Bug #2). **Fix:** `BaseBot._extract_shares()` reads `shares_bought`/`shares`/`shares_filled`, and if still zero derives shares from the fill price (`amount / fill_price`, or `amount / (1-yes_price)` for NO bets) so a share count is always recorded. Trades already logged with `shares_bought=0` can't be backfilled (entry price is lost) and stay at $0.

9. **Wrong market traded — next-day 15-min window selected as "current" (CRITICAL):** Bots placed trades on `Bitcoin Up or Down - July 13, 8:15AM-8:30AM ET` — a *next-day*, *15-minute* market — and the dashboard showed it as the Current Market. Two independent root causes combined:
   - **No 5-minute filter.** `market_utils.is_5min_market()` existed but was *never called*. Discovery and the dashboard accepted any BTC "up or down" market via `is_btc_updown`, so 15-min windows passed straight through into the trade pool.
   - **Date-blind window matching.** `window_contains_now()` parsed only the ET *time-of-day* from the question and compared it to the current ET time, ignoring the calendar date. At 8:29 AM ET on the 12th, tomorrow's `8:15–8:30` window "contained now" and was selected as current (the candidate filter used `... or window_contains_now(...)`). The dashboard had a duplicate `_window_contains_now` with the same flaw.

   **Fix:** Added `market_utils.select_current_market()` — a pure selector that picks the live window by its **real `resolves_at` timestamp** (`0 < time_remaining_seconds <= 300`), never by time-of-day, and requires a genuine 5-minute window. `arena/discovery.py` now gates the *entire* market pool through `is_5min_market` (trader, maker fallback, and `all_markets` snapshot can never see a 15-min window) and selects via the new function. `dashboard/server.py` applies the same 5-min gate and keys `is_current_window` off the real timestamp only. Both date-blind `window_contains_now` helpers were deleted so they can't be re-introduced. Regression locked in by `tests/test_market_selection.py`. **Lesson:** identify the live window by `resolves_at`, not by re-parsing the question's clock time — the question carries a date the time-of-day regex throws away.

10. **"Phantom" trades — Simmer's 50-buys/day cap mislogged as fills (CRITICAL):** ~70% of logged paper trades carried no Simmer `trade_id`, `shares_bought=0`, and (via the price-fallback) fabricated P&L. Root cause: **Simmer's free SDK tier caps at 50 buys/day/account.** Past 50, `POST /api/sdk/trade` returns **HTTP 200 with `{success:false, trade_id:null, shares_bought:0, error:"Daily trade limit reached"}`**. `_execute_paper()` only checked the HTTP status — never the `success` field — so every rate-limited rejection was logged as a real trade, and `_extract_shares()` invented a share count from market price, which the resolver turned into fabricated win/loss P&L. Confirmed: `trade_id`-carrying trades capped at *exactly* 50/day. All 4 bots share ONE Simmer account (only the default key authenticates — see BUG #? / [[simmer-bot-keys-placeholder]]), so bots trading late in the loop (e.g. `phantom-v1`) were 100% starved. Discovered via a safe `dry_run:true` POST.

    **Fix (venue rework):** Paper fills no longer depend on Simmer. `venues/paper.py` computes each fill **locally** from the real market price (`shares = amount / entry_price`, `fill_source='local_sim'`), so paper trading is unlimited and honest; the resolver settles it against the real market outcome. Simmer is now an opt-in cross-check only (`config.SIMMER_MIRROR_ENABLED`, default off) and its response is checked for `success:true` + `trade_id` before being trusted. Also removed the 1h stale-expiry — pending trades stay pending until the market actually resolves (Simmer can take a day). New `fill_source`/`entry_price` columns record how every trade filled. **Lesson:** an HTTP 200 is not a fill — check the body's `success` flag; and don't let a third party's rate limit silently corrupt your P&L.

11. **`phantom-v1` declared the wrong `strategy_type`:** `PhantomBot.__init__` passed `strategy_type="hybrid"` to `super().__init__` then reassigned `self.strategy_type = "phantom"` afterward. It happened to work (base signal tables have a `phantom` entry and the lookups run at decision-time), but it was fragile and would break if the base ever read `strategy_type` during `__init__`. **Fix:** pass `strategy_type="phantom"` directly.

12. **Time-gated maker locked out of its own entry window — `late-window-maker-v1` had zero trades:** The secondary/maker tick (`arena._run_maker_section`) marked a **HOLD** into the `(bot, market_id)` dedup set (`state.mark_traded(key)`), same as an actual trade. But the maker section sees each market up to `MAKER_UPCOMING_WINDOW_SEC` (20 min) early, in PRE-WINDOW mode. `LateWindowMaker` deliberately holds until the final ~90s of the window — so on the *first* PRE-WINDOW cycle it returned `hold`, got marked "traded", and `is_traded()` then short-circuited every later cycle, including the final-90s window that is the entire strategy. Result: the bot could **never** trade. (`fee-zone-maker-v1` was hit less — it has no hard time gate, so it occasionally fired on the first cycle it saw a qualifying market before being marked.) **Fix:** don't add HOLDs to the dedup set — only a real execute attempt (or a trade exception, to prevent poison busy-loops) marks the pair. The maker section now re-evaluates each 20s discovery cycle with fresh `time_remaining`/price until it either trades or the window rolls over. Regression locked in by `tests/test_maker_section.py`. **Lesson:** a HOLD is not a trade — dedup must key on *acted*, not *evaluated*, or any time-gated strategy that must wait will be starved. (Same spirit as the primary-bot "re-evaluate every tick" fix, which had not been applied to the secondary tick.)

13. **Dashboard prices looked "stuck at 51¢/50¢" — blocking I/O in `async def` endpoints starved the event loop:** The prices were actually *fresh* on the backend, but a single `/api/markets` call took **~11s** on the running server. Root cause: the FastAPI dashboard endpoints were declared `async def` yet called **blocking** `requests`/DB I/O directly. Blocking calls in an async endpoint run *on the event-loop thread*, so with the frontend polling `/api/markets` every 3s and `/api/price` every 1s, the blocking network calls serialized and piled up into 10s+ latencies — the market cards showed the pre-window 50/50 seed (0.505 → 51¢/50¢) for long stretches because the fresh response landed seconds late. **Fix (two parts):** (a) converted every blocking GET endpoint from `async def` to plain `def` so Starlette runs them in its threadpool (concurrent, never blocking the loop) — the 5 POST handlers that `await request.json()` stay async; (b) added `polymarket_markets.midpoints_batch()` / `price_markets()` using the batch `POST /midpoints` CLOB endpoint so a whole discovery snapshot is priced in ONE round trip (~5× faster than per-market `/midpoint` GETs) with layered fallback (batch → single `/midpoint` → order-book mid). After: 6 concurrent `/api/markets` all return in ~1.3s and light endpoints stay at single-digit ms under load. Covered by `tests/test_pricing.py`. **Lesson:** never call blocking I/O from an `async def` FastAPI handler — either make the handler a plain `def` (threadpool) or await a real async client. A "stuck price" is not always a stale-data bug; check endpoint *latency* first. NB: 0.505/0.495 (→51¢/50¢) is the genuine Polymarket pre-window placeholder quote — a market that hasn't opened yet legitimately sits at 50/50; only the live window (`time_remaining ≤ 300s`) carries a real price.

14. **Arbitrage bot was the arena's biggest loser (−$84 over 190 legs) — negative-edge, unbalanced "arb" (CRITICAL):** A market-neutral arb should never be net-negative, yet `arbitrage-v1` bled ~$84 with a tell-tale 50% "win" rate (one leg wins, one loses). Two independent root causes, both visible in the resolved legs: (a) **edge measured at the top of book, position sized far past it.** `make_decision` computed `edge = 1 − (yes_best_ask + no_best_ask + fees)` from `best_ask` — the single cheapest share — but `execute` then filled ~20 shares per leg, walking *down* the book into worse prices. The realized VWAPs summed to **≥ $1.00** in nearly every pair (0.99–1.02), i.e. there was never real edge once slippage was included; e.g. one market fired on best-asks < 0.99 but filled at YES 0.95 + NO 0.06 = 1.01. (b) **legs weren't share-matched.** Each leg was sized in *dollars* (`target_shares × price × 1.02`, capped at `max_pos`) and filled independently, so the share counts diverged badly (e.g. 27.2 NO vs 17.8 YES) — leaving a naked directional tail that lost ~$1 per excess share. **Fix (three parts):** (1) added `polymarket_fills.simulate_fill_shares(book, n)` — a share-count-based book walk (fixed shares, variable cost) alongside the USD-budget `simulate_fill`; (2) `PaperEngine.place` / `LiveEngine.place` accept `target_shares=` to fill an *exact* share count (paper skips if depth can't fill it in full or the shared bankroll can't afford it); (3) the arb now sizes **both legs to the same share count** (`min` of the two books' fillable depth, capped by `max_pos` and available bankroll) and computes edge from the **depth-walked VWAP** for that size — firing only when `shares − (yes_cost + no_cost + fees) ≥ ARBITRAGE_MIN_MARGIN × shares`. Regression locked in by `tests/test_arbitrage.py` (thin-top-of-book trap → skip; fired legs are share-matched; matched size ≤ thinner book) and `tests/test_venues.py` (exact-share fills, depth-insufficient skip). **Lesson:** an arbitrage edge must be measured against the *executable* price for the *intended size* (depth-walked VWAP), never the top-of-book quote — and the two legs must be share-matched or the position isn't neutral. `best_ask` is a one-share price; sizing past one share without re-pricing is how a "risk-free" strategy becomes the biggest loser.

15. **Maker bots ran outside the startup slate — dashboard showed 7 bots when 5 were selected:** `late-window-maker-v1` and `fee-zone-maker-v1` were created unconditionally by `_create_maker_bots()` in `main_loop`, completely separate from the interactive startup selection, so they always ran (and traded) regardless of the chosen slate — surprising the operator with two "extra" active bots. **Fix:** folded both makers into `startup.STRATEGY_MENU` and the default lineup (`DEFAULT_INDICES` → 7 bots), so they are selectable and appear in Active Bots by choice. `main_loop` now partitions the launched slate into trader bots (1s tick + evolution) and maker bots (discovery-cadence maker section) via `MAKER_TYPES`, and `_resolve_maker_bots` rebuilds the maker set from DB configs on the 'continue' path. Regression: `tests/test_startup.py` asserts the 7-bot default incl. both makers.

16. **Setting the paper bankroll didn't reset the visible balance to the entered figure:** The dashboard "Balance" shows `available = bankroll + realized_pnl − reserved_open`, but the Settings field set the raw `bankroll`. So entering $200 after the arena had lost ~$82 and reserved ~$59 in open positions left available at ~$59–104, not $200 — correct accounting, confusing UX. **Fix:** the field now **tops the pool up to the entered figure** via `db.topup_paper_bankroll(target)`, which back-solves `bankroll = target − realized + reserved` so `available` equals what you type *without* discarding trade history or un-reserving live positions (the identity stays sound through later resolutions). UI relabeled "Paper Balance", pre-fills the current available, and confirms "Balance topped up — available now $X." Regression: `tests/test_venues.py::test_topup_sets_available_to_entered_amount_after_losses`. **Lesson:** P&L was never wrong here — "available cash" and "starting bankroll" are different quantities; the reset action has to operate on the one the user is looking at.

17. **Divergent taker-fee formula in `fee_zone_maker` — bogus quadratic vs the official linear formula:** `bots/bot_fee_zone_maker.py` carried its own local `taker_fee(price) = 0.25 × (p·(1−p))²` (docstring cited a "Polymarket Jan 2026 update"), while the settled-P&L path (`polymarket_fills.taker_fee`) used the correct `feeRate × shares × p × (1−p)`. The quadratic understated fees and had the wrong *shape*, diverging most at the price extremes — exactly where the arbitrage bot trades. Verified against the official docs (https://docs.polymarket.com/trading/fees): the real formula is **`fee_usdc = feeRate × shares × p × (1 − p)`**, symmetric around 50¢, makers pay zero, and the crypto tier `feeRate = 0.07` peaks at **$1.75 per 100 shares** at 50¢ (`0.07 × 100 × 0.25 = 1.75`). So `polymarket_fills.taker_fee` and `config.POLYMARKET_TAKER_FEE_RATE = 0.07` were already correct for BTC (crypto) markets; only the maker's local copy was wrong. **Fix:** deleted the quadratic and made `fee_zone_maker.taker_fee` a thin wrapper over `polymarket_fills.taker_fee(1.0, price)` so there is ONE fee formula in the codebase; corrected the docstring + fee table (60–82¢ zone is ~103–168 bps, not the old 64–144). Regression: `tests/test_maker_section.py::test_fee_zone_taker_fee_matches_canonical_polymarket_formula` asserts the two match and that the crypto peak is $1.75/100sh. **Lesson:** a fee formula is P&L-critical and belongs in exactly one place — any bot needing it must call the shared function, never re-derive it from a half-remembered blog number. Other fee tiers per the docs (not needed here, all our markets are crypto): Sports 0.05, Finance/Politics/Tech 0.04, Geopolitics 0 (fee-free). NB: the standalone `bot.py` (a SOL/USDC swing-trading skeleton, not part of the arena) has an unrelated `FEE_RATE = 0.001` — that's a generic CEX fee, not Polymarket, and is intentionally left alone.

18. **Arbitrage still net-negative — decision and fill used *different* book snapshots (CRITICAL, follow-on to #14):** After #14 made the arb's *decision* depth-aware and share-matched, `arbitrage-v1` was **still** the arena's biggest loser (−$9 over 18 legs, 50% "win" rate). Every resolved pair had YES+NO **entry** prices summing to **>$1.00** (1.01–1.07) — impossible for a real arb. Root cause: `make_decision` validated the edge on the warm-store book snapshot, but `execute()` handed fixed `target_shares` to `PaperEngine.place`, which **re-read a *fresh* book per leg** (`venues/paper.py`) — and the two legs filled ~1s apart. The DB reasoning proved it: a pair logged `ARB edge=+0.0228/pair (yes_vwap=0.240 no_vwap=0.710)` = sum 0.95 at decision, but *filled* at yes 0.310 + no 0.700 = 1.01. Because YES+NO best-asks naturally rest just **above** $1 (the market's vig) and BTC 5-min prices move fast, the fleeting sub-$1 window the decision saw was gone by fill time — so nearly every "arb" filled at a guaranteed loss. This is a decision→execution snapshot race, not a fee or sizing bug (fees were already correct). **Fix (three parts):** (1) `ArbitrageBot.execute()` now **re-reads both books, re-simulates the matched fill, and re-checks the combined edge ≥ margin on that fresh snapshot** — aborting with `arb_edge_gone` and placing *nothing* if the edge evaporated; (2) both engines accept `book=` so the arb fills each leg against the **exact snapshot it just validated** (no third re-read), plus a per-leg `limit_price` guard; (3) a general **slippage guard** (`config.MAX_FILL_SLIPPAGE = 0.03`) now protects *every* bot — `PaperEngine`/`LiveEngine` reject a BUY whose realized avg price drifts more than 3¢ above the price the decision expected (`reason="slippage_exceeded"`), driven by a new `entry_price` field on every buy signal (`base_bot.make_decision`, both makers). `ARBITRAGE_MIN_MARGIN` bumped 0.01→0.02 for extra cushion. Regression: `tests/test_venues.py` (limit-price reject, passed-book determinism) and `tests/test_arbitrage.py` (execute aborts when edge gone at fill; fills both legs share-matched when it holds). **Lesson:** an arbitrage isn't real unless it is *validated and filled on one atomic snapshot*. Measuring the edge on snapshot A and filling on snapshot B — even 1s later — reintroduces exactly the loss #14 tried to kill, because the vig means the book's default state is *no edge*. More broadly: any strategy with a cents-thin edge must carry its expected price into execution and refuse fills that drift past it.

19. **Both maker bots were starved by price-band gates 5-min markets rarely occupy:** `late-window-maker-v1` had **zero** trades and `fee-zone-maker-v1` had **one** all session. Not crashes — the gates almost never opened. FeeZoneMaker only quotes YES in [0.60, 0.82]; over 184 maker cycles the price was in that band just **9%** of the time (5-min BTC markets resolve toward 0 or 1 quickly, rarely lingering mid-book). LateWindowMaker requires, in the final 90s, YES ∈ [0.58, 0.92] **and** positive BTC momentum ≥0.08% — but by T-90s the market has usually already resolved to an extreme (logs show final-90s prices of 0.03, 0.02, 0.01, 0.005 on down markets), so the band was essentially never occupied that late, and the ~23s maker cadence gave only ~4 shots inside the 90s window. **Fix (retune, to be validated by live data):** FeeZone band widened to [0.56, 0.86] (still all ≥80 bps taker fee); LateWindow window widened 90→150s (more shots, catches the market before it fully resolves), `min_momentum` 0.0008→0.0005, band [0.56, 0.90] — the max cap stays ≤0.90 to respect the break-even rule ([[entry-price-breakeven-rule]]: buying YES as a taker above ~0.90 needs an implausible win rate). **Lesson:** a gate tuned for a slower market starves in a fast one — 5-min BTC windows spend almost no time in the mid/high price band, least of all near expiry. These are directional retunes to reduce starvation, not optimized params; recheck once trades accumulate.

20. **YES-only NO ban forfeited the entire NO side of the book:** 100% of directional trades were YES; the DB held zero NO fills across every bot. `base_bot.make_decision` collapsed the signal stack to a scalar `combined`, set `side = "yes" if combined > 0 else "no"`, then hit a blanket `if side == "no": return skip` ("NO ban") — inherited from the forked codebase and justified by a stale Simmer-era stat (NO 44% WR, −$132 all-time). Every downstream piece already supported NO: each strategy's `analyze()` natively returns NO on its own logic (momentum on `pct_change<0`, mean_reversion on overbought RSI, sentiment on bearish, hybrid on a negative weighted vote); `venues/paper.py`/`live.py` pick the NO token/book and fill against the NO price when `side=="no"`; `learning.record_outcome` records NO outcomes coherently (a NO win increments the YES-loss counter, keeping the learned bias a YES-probability); and `market["no_price"]` is populated by the warmer and threaded onto the hot-path dict by `arena/trader.py`. Only `make_decision` blocked NO — and its guards/sizing referenced the YES price, so even lifting the ban would have sized a NO trade against the wrong book. **Fix:** replaced the sign-then-ban logic with a two-sided **net-edge** comparison. The signal stack is reinterpreted as a fair YES probability (`fair_yes = yes_mid + price_tilt + alpha`, where `price_tilt = (yes_mid−0.5)·aggression·K_TILT` is the favorite-following lane and `alpha` is the summed secondary lanes — identity `price_tilt + alpha == old combined` preserved, and `config.K_TILT = 0.5` keeps YES behavior numerically identical at `aggression == 1.0`). Then for each side, `edge = prob − side_price − taker_fee(1, side_price)` (fee via the canonical `polymarket_fills.taker_fee`, never re-derived — see #17); the bot buys whichever side has the larger positive edge above a per-strategy `MIN_EDGE` floor, and skips if neither clears it. Guards became **symmetric** — a bot skips any *chosen* side priced `> config.HIGH_PRICE_GUARD` (0.72) or `< config.CONSENSUS_GUARD` (0.35). Shares-first sizing, `entry_price`, and the slippage limit now all key off the chosen side's price. A directional bot still takes at most one side per market (argmax); arbitrage remains the only two-legged bot. When the two mids are exactly complementary the comparison reduces to the old sign decision, so the two-sided value only materializes when the NO book diverges from `1 − yes` — the opportunity the ban was throwing away. Regression: `tests/test_two_sided.py` (11 tests — NO chosen on book divergence, YES parity on favorites, symmetric guards on the NO price, both-negative skip, complementary-mids-reduce-to-sign). **Three more bots carried their own independent NO bans outside the base path and were lifted too** (`tests/test_no_side_bots.py`): `bot_sniper` (overrides `make_decision` with price-zone rules — its NO-zone `skip` was replaced by a symmetric mirror that applies the same cheap/strong zones to the NO token's price with DOWN-momentum confirmation); `bot_late_window_maker` (its `if momentum < 0: hold` NO ban became a NO quote on the NO price when momentum is down); and `bot_fee_zone_maker` (YES-only by construction → now quotes whichever side's price sits in the fee zone, fee being symmetric `fee(p)==fee(1−p)`). The mean-rev SL/TP variants call `super().make_decision` so they inherited the two-sided base behavior automatically (only their docstrings were stale). Arbitrage is the only two-legged bot; every other bot takes at most one side per market. The sniper/maker NO branches are symmetric mirrors **not yet validated by live NO data** — recheck once NO trades accumulate, same as the maker retunes in #19. Design + plan under `docs/superpowers/`.

21. **Anti-predictive signals + fake-edge confidence + a net-harmful stop-loss (overnight run analysis):** After an overnight paper run (655 trades, −75.16 P&L, ~62% resolved WR), a log analysis found the loss was NOT random — it was structural. Decomposition: win +929 / loss −831 / **exit_sl −174**. Root causes, each measured over 460 directional trades (confirms-chosen-side WR vs contradicts-side WR): **(a) the learning bias was anti-predictive (−24pp: 53.5% vs 77.6%)** — mechanically correct code but conceptually broken (coarse feature buckets carry no persistent edge in a fast near-efficient market, the price bucket double-counts the market-price signal already in `price_tilt`, and it overfits per-bot on tiny samples); **(b) OBI was anti-predictive (−8.6pp: 58.1% vs 66.7%)** — resting-depth is a fade signal, while **CVD (executed aggression) was the ONE real edge (+14.5pp: 66.9% vs 52.4%)** yet was underweighted; **(c) the composite `edge` that drives side-selection AND confidence had ZERO discriminative power (60.6% vs 61.0%)** because the good signal was cancelled by the two bad ones — so `confidence = edge × K` was meaningless (conf 0.5–0.7 → 73% WR but ~$0 P&L, entering at 0.73 avg; conf ≥0.7 → net loss); **(d) the `price_tilt` manufactured fake edge at efficient extremes** (favorite underpricing is flat ~+5¢ across 55–85¢, not proportional to distance from 0.5, so an uncapped linear tilt over-bet ≥75¢ where WR≈price after fees); **(e) the per-strategy `analyze()` fired in only 6.6% of trades** — all directional bots traded the identical base stack, so evolution was selecting among clones; **(f) the stop-loss was net-harmful** — the hold-to-resolution counterfactual (−150.7) beat stopping (−172.3), because a −25% stop on a position that fully resolves in ~5 min just converts intra-window noise into locked losses (mean-rev entries were ~break-even even held). **Fixes (Phases 1–2):** `SIGNAL_WEIGHT_OBI 0.10→0`, `SIGNAL_WEIGHT_CVD 0.10→0.25`, `LEARNING_ENABLED=False` (outcomes still recorded; edge-calibrated learner is the deferred Phase 3 redesign), `price_tilt` capped at `±FAVORITE_EDGE_CAP` (0.06), stop-loss removed from `mean_reversion_sl` (+ its now-unjustified 1.5× oversizing), and the four strategies re-tuned to fire often with genuinely distinct theses (momentum threshold 0.2%→0.03%; mean-rev single z-score fade, lookback 20→10; sentiment repurposed to Polymarket in-market sentiment since the social feed never existed post-Simmer; hybrid ensemble threshold 0.55→0.15) at `STRATEGY_SIGNAL_WEIGHT 0.15→0.30`. Coin-flip (45–55¢) bleed is suppressed by the existing `MIN_EDGE` gate on a now-real edge — **not** a price-bucket ban (explicitly ruled out). Regression: `tests/test_signal_reweight.py` + `tests/test_strategy_differentiation.py`. **Lesson:** a losing bot is a *measurement* problem before it is a *tuning* problem — decompose P&L by outcome, then measure each signal's realized predictiveness (confirms vs contradicts WR) before touching weights. Two of the six signals were actively inverted; the "learning" system was making decisions worse, not better; and "confidence" meant nothing because the edge feeding it was noise. Validate the fixes by re-running the per-signal + price-bucket queries once ~50+ trades accumulate.

22. **Model was blind to the "price to beat", flooded into NO, and NO was a symmetric mirror of YES:** A follow-up run after #21 was still net-negative (~55% WR), with bots visibly over-eager to bet NO early in the window. Independently, live per-lane attribution (sign-vs-outcome on real fills, parsed from trade reasoning) reconfirmed #30's `strat` finding harder — `|strat| < 0.3` was the ONLY profitable band (+$41.23) while ≥0.6 ran 46% WR / −$34 — and showed evolution churning on noise (cycle 6 killed `sniper-v1` on a 17-trade / −$8.49 dip one cycle after it survived at 61%, and "judged" freshly-spawned mutants on 1–2 trades). **Fix (four):** (1) a **drift-conditional dead-zone gate** in `make_decision` (fires before the edge gate): a directional bot sits flat when the chosen side's MID is in `[DEAD_ZONE_PRICE_LO, DEAD_ZONE_PRICE_HI]` (0.42–0.58) AND `|drift| < DEAD_ZONE_DRIFT_MIN` (0.10) — regime-agnostic, and `|drift| ≥ 0.10` in the band passes through so the profitable market-lags-drift trades are untouched. (2) `STRAT_LANE_CONF_CAP` 0.60 → **0.30**, clamping the lane to the only magnitude band that ever profited. (3) `MIN_TRADES_FOR_JUDGMENT` 15 → **30** — a 5-min-market window under ~30 resolved is noise, and evolution was replacing survivors on it. (4) a **closed-loop auto-approve promoter** (`arena/lane_promoter.py`) that flips the Signal Lab pipeline's judge from the optimistic offline harness to **live shadow attribution**: candidate lanes still get nominated by the harness, but a proposal is only auto-approved (dashboard toggle, default ON, bounded to one promotion/cycle under an active-lane cap) once the lane's own `cand(...)` reads — logged in every directional trade pre-kill-switch, i.e. measured at zero live weight — clear a LIVE accuracy bar (`AUTO_APPROVE_MIN_ACCURACY` 0.55 over `AUTO_APPROVE_MIN_TRADES` 60), deliberately stricter than the monitor's 0.53 demotion floor (hysteresis). Off → the promoter still attaches the live evidence to each proposal for a human click; demotion (`arena/lane_monitor.py`) stays automatic either way. **Counterfactual:** removing the 59-trade dead-zone cluster alone lifts the run from +$14 to roughly +$92, holding all else constant. **Lesson:** a signal being predictive in isolation (harness follow-WR, or a lane's raw sign) is not the same as it *adding money at the executable price* — the dead-zone trades cleared MIN_EDGE and the tax yet lost, and the harness approved `tech` at 74–80% that scored 51.7% live; the only trustworthy judge is realized live P&L, so both the trade gate and the promotion loop now key off it.
